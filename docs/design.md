# 设计

本文档作为 Eevee 的高层设计，覆盖意图、权衡和代码无法表达的领域规则；当前行为以代码为准。

## 愿景

### 背景

一项长期工作往往由许多性质不同的子任务组成，以 Agent Session 为工作形态会遇到一些瓶颈：

1. **人的注意力有限**：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。
2. **模型注意力涣散与串行阻塞**：单会话里长耗时任务（如跑仿真、编译）会阻塞前台对话，不同任务的中间细节混在一起也会降低模型表现。
3. **长上下文成本**：超出 Cache TTL 后，`Input` 或 `CacheWrite`将消耗大量额度。

### 设想

Eevee 是一个基于 Pi-Durable 的 Proactive Agent，会话退化为底层实现细节，用户面对一个持续工作的助手：

- **`Router` / 调度者**：用户对话的主要入口，负责理解目标、统筹规划、建立工单、成果验收。
- **工单（`Ticket`）**：基础任务单位，记录目标、输入、验收与产物。
- **`Worker` / 执行对话**：每张工单绑定一个 Worker 会话，Worker 可以使用各类能力并管理自己的后台任务。
- **报告（`Report`）**：Worker 与 Router 之间的协同接口。
- **记忆（`MemoryDrive`）**：有价值的经验存入 Git 记忆仓。

用户通常只与 Router 对话，但可以随时观察 Worker 的完整执行过程，直接发送引导或打断它。

#### 示例：论文项目

1. 用户新建项目“光学论文《xxx》”，系统创建项目存储与 Git 记忆仓库。
2. 与用户讨论后，Router 建立 Ticket 1“打磨论文草稿”，T1 的 Worker 开始工作。
3. T1 发现缺少仿真数据，交一份 `waiting` 报告写明需要什么资料；Router 建立 Ticket 2“运行仿真”，并指定 T2 的结果交给 T1；仿真参数需要用户拍板时，Router 先用 `ask_user` 提问，之后照常处理其他事情。
4. T2 启动两小时仿真，命令转入后台；仿真结束后作业结果唤醒 T2 处理数据，交付 `ready` 报告。
5. Router 验收 T2 后，Engine 把 T2 的报告和产物投放给 T1，T1 继续推进论文打磨。

### 原则

1. **占用人尽量少的注意力，产出尽量多的价值**：只在用户必须做决定、或者有成果值得展示时才通知；其余时间保持安静。
2. **YOLO**：不设置逐命令审批。
3. **降低认知负担**：新需求优先考虑能否复用现有概念。
4. **状态持久化**：任何 `reset` 后还需要的信息（工单、依赖、待回答的问题）均可恢复状态。
5. **可观测、可控制**：每个工单、Worker 和后台作业都能查看，用户随时可以中止或介入。

## 概念

### 核心概念

| 概念 | 代码名 | 定义 |
|:-:|:-:|---|
| 项目 | `Project` | 一个持续工作的项目：一个 Router、一组工单、记忆库和持久对话状态 |
| 调度者 | `Router` | 项目的根对话与用户的主要入口，负责全局规划、工单协调、报告处理和长期记忆 |
| 工单 | `Ticket` | 一项独立工作的协调外壳，与一个持续的 Worker 主对话一一对应 |
| 执行者 | `Worker` | 工单对应的会话，负责执行任务；用户可以发送引导消息 |
| 报告 | `Report` | Worker 与 Router 之间的自动协同结果，分为中途报告与收尾报告 |
| 记忆库 | `MemoryDrive` | 基于 Git 的 Markdown 笔记仓库，分项目级和全局两份 |

### 支撑概念

这些概念服务于核心模型：

| 概念 | 代码名 | 作用 |
|:-:|:-:|---|
| 提问 | `Question` | 需要用户决定时的一组结构化问题 |
| 运行 | run | 对话从收到一条消息开始，到最终回答、被打断或失败为止的一次连续执行 |
| 轮次 | turn | 一次运行里，模型每请求一批工具调用为一个轮次 |
| 后台作业 | `Job` | Worker 的长时命令或其他后台执行，完成后可以唤醒所属 Worker |
| 角色 | `Role` | 一类对话的提示词、Opening 与 Extension 能力配置 |
| 开篇 | `Opening` | 对话创建或 `reset` 时生成的开场材料，具体组成属于实现策略 |
| 资源地址 | URI | 引用持久对象的统一写法，如 `ticket://t12`、`report://t12#3` |
| 工作目录 | `Workspace` | 用户自己的项目目录（一个项目可有多个），产物默认写在这里 |
| 模型画像 | `ModelProfile` | 模型客观参数与用户记录的使用经验，供需要时选择模型 |
| Engine | `Engine` | 常驻后台的 Node.js 进程，承载全部项目与本地 WebUI |

系统内部还有 `dreamer` 执行配置，用于记忆整理工单；具体职责与 Extension 配置见 [角色与能力](#角色与能力)。

### 状态

- 工单只有 `open` / `done` / `cancelled` 三种状态。
- 工单可以声明把验收后的结果交给哪些工单；报告和问题都归属于某张工单或 Router。

### 数据归属

| 存储 | 内容 | 来源 |
|:-:|:-:|:-:|
| `session.sqlite` | 全部对话记录；工单、报告、问题文档 | Engine |
| 记忆库 | 记忆 | `memory`、Dreaming、用户 |
| 工作目录 | 用户的项目文件与产物 | Worker、用户 |
| `~/.eevee/` 配置文件 | 凭据、模型配置、模型画像、MCP 服务、角色能力配置与运行策略 | Engine、用户 |

## 角色与能力

### 职责

| 角色 | 职责 | 基础能力 | Opening |
|---|:-:|---|:-:|
| `router` | 全局规划、工单协调、报告处理、验收与记忆 | 管理工单、提问、读取、编辑记忆、交接重置；没有工作区写入与命令执行 | 记忆 + 项目概况 + 工单一览 + 交接信息 |
| `worker` | 在 Ticket 目标内自主完成工作，管理自己的执行过程，并通过 Report 协同 | 读写文件、执行命令与后台作业、提交报告 | 记忆 + 工单 + 最新报告 |
| `dreamer` | 内部记忆维护配置，不构成独立的产品角色 | 读取记录、整理记忆、提交报告 | 记忆 + 待整理记录 |

### 组成

一个角色由三部分组成：

- **固定提示词**：描述职责、协同方式与行为原则。
- **Opening**：在对话创建或重置时生成开场材料，具体组成属于可调整的上下文实现策略。
- **能力配置**：选择该角色需要的 Durable Extension，并按需调整工具和模型。

### Extension

1. **安装**：Engine 把 Extension 注册到 Registry。扩展使用 Durable Extension API，MCP 服务可以由桥接 Extension 接入。
2. **按角色启用**：已安装的 Extension 可为每种角色分别配置启用与否。
3. **向模型呈现**：已启用 Extension 的工具可以直接提供，也可以按需暴露，避免工具过多挤占上下文。

### 配置

角色配置所有项目共用，可以在面板或配置文件里调整，修改对之后的运行生效：

- **按角色启用扩展**：在角色自带能力之上，为每种角色选择额外的 Extension（如 MCP 服务）。
- **运行上限**：限制一次运行的轮次，避免执行对话无止境地运行。
- **容错**：已启用但后来卸载的扩展在应用时跳过，不影响角色的其他能力。

## 工单与调度

总体设计：正常路径自动流转，意外情况交给 Router，必须由用户决定时才提问。

### 拓扑

**自动协调经过 Router，数据通过文件和地址传递；用户可以直接介入任何 Worker。**

- Router 掌握全局目标，安排工单、优先级与时序，处理报告、验收和异常。
- Router 没有工作区写入与 `bash` 工具，避免它亲自干活而阻塞全局协调。
- 确定事项由 Engine 投递，依赖工单的结果、问题的回答、后台作业的结果，由 Engine 按规则直接投给对应 Worker。

### 主动推进

每份收尾报告带一个“已处理”标记（`handled`），使未处理结果成为 Router 的持久待办：

- **持续可见**：未处理报告保留在 Router 待办中。Engine 可以提醒 Router。
- **交给用户**：Router 仍无法推进或需要用户决定时，报告进入面板“等待介入”区。

### 对齐与验收

- **需求对齐**：讨论清楚后建立工单；需求模糊时，Router 从工作目录、记忆等收集信息，可以建立工单辅助探索；需要用户介入的分歧才提问，并附带推荐答案。
- **执行对话的疑问**：写进报告，Router 能自己回答就直接回复 Worker，否则转给用户，用户的回答直接投递给相应执行对话。
- **验收**：验收通过必须附带证据，记在工单上。

## 记忆

### 范围

记忆收录跨会话长期有用的合作经验，分为项目与全局两种范围。

记忆系统由 Git 提供支持，但将细节与机制进行封装，对外暴露为 `memory` 工具及编辑界面。

### 格式

- `MEMORY.md`：常驻索引，控制在 200 行以内，包含指向主题文件的索引和简要说明。
- 项目中的主题文件按内容组织经验条目，每条附来源和日期；全局约定保持集中。

### 读取

- **常驻**：全局和项目的 `MEMORY.md` 放在每个对话的开篇最前面，运行中途不变。
- **按需**：模型根据索引读取相关主题，不把全部历史塞进每次对话。
- 已生效的记忆会进入之后新建或重新开始的对话；待审批的提案不作为既定经验。
- 读取文件与历史不产生变更，不能因为查看记忆就顺带保存手动修改。

### 写入

执行对话只读不写：发现的经验写进报告，由 Router 或 Dreaming 提炼；用户可以直接从 Web UI 编辑记忆，这些修改直接生效，记录为用户变更。

Router 和 Dreaming 对两个记忆库的所有修改都只能提出提案，只有用户批准后才生效。

### Dreaming

Dreaming 是后台记忆维护能力，它顺着地址回顾近期记录和现有记忆，尤其是反映真实执行结果的工具输出与报告里的经验教训，提出四类整理建议：

- **合并重叠笔记**：把同类条目整合进清晰的主题文件；
- **剔除临时细节并纠错**：删掉只对单次调试有效的信息，订正被后续执行推翻的旧笔记并注明来源；
- **清理陈旧记忆**：移除已经失效或长期没有价值的条目；
- **补漏与整理索引**：补录漏记的经验，维护 `MEMORY.md`，把过长的项目细节下沉到主题文件。

**触发**：自上次整理以来积累了足够的新材料，且项目空闲一段时间后，Engine 发布整理工单。

## 用户界面

### 原则

1. **简洁**：减少注意力分散，利于心流状态。
2. **布局自解释**：减少标语、提示文字和次要标签，让界面无需借助说明就能看懂。
3. **注重体验**：User/Developer/Agent Experience.
