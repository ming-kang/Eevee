# 愿景

## 背景

一项长期工作由许多性质不同的子任务组成，以 Agent Session 为工作形态会遇到一些瓶颈：

1. **人的注意力有限**：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。
2. **模型注意力涣散与串行阻塞**：单会话里长耗时任务（如跑仿真、编译）会阻塞前台对话，不同任务的中间细节混在一起也会降低模型表现。
3. **长上下文成本**：超出 Cache TTL 后，`Input` 或 `CacheWrite`将消耗大量额度。

## 设想

Eevee 是一个基于 Pi-Durable 的 Proactive Agent，会话退化为底层实现细节，用户面对一个持续工作的助手：

- **`Router` / 调度者**：类似于机场塔台与铁路调度，是用户对话的主要入口，负责理解目标、统筹规划、安排优先级、建立工单、处理报告和成果验收，不亲自执行耗时工作。
- **工单（`Ticket`）**：基础任务单位，记录目标、输入、验收与产物。
- **`Worker` / 执行对话**：每张工单绑定一个 Worker 会话，Worker 可以使用文件、命令、MCP、Extension 等能力，还能管理自己的后台作业。
- **报告（`Report`）**：Worker 与 Router 之间的协同接口，正常结果由 Report 回流，Router 不需要逐条转述执行细节。
- **记忆（`MemoryDrive`）**：有价值的经验存入 Git 记忆仓库，可以读取、更改。

用户通常只与 Router 对话，但可以随时观察 Worker 的完整执行过程，直接发送引导或打断它。Worker 不独立向用户推送通知，协调仍通过 Router 调度。

### 示例：论文项目

1. 用户新建项目“光学论文《xxx》”，系统创建项目存储与 Git 记忆仓库。
2. 与用户讨论后，Router 建立 Ticket 1“打磨论文草稿”，T1 的 Worker 开始工作。
3. T1 发现缺少仿真数据，交一份 `waiting` 报告写明需要什么资料；Router 建立 Ticket 2“运行仿真”，并指定 T2 的结果交给 T1；仿真参数需要用户拍板时，Router 先用 `ask_user` 提问，之后照常处理其他事情。
4. T2 启动两小时仿真，命令转入后台；仿真结束后作业结果唤醒 T2 处理数据，交付 `ready` 报告。
5. Router 验收 T2 后，Engine 把 T2 的报告和产物投放给 T1，T1 继续推进论文打磨。

## 原则

1. **占用人尽量少的注意力，产出尽量多的价值**：只在用户必须做决定、或者有成果值得展示时才通知；其余时间保持安静。
2. **YOLO**：不设置逐命令审批。
3. **降低认知负担**：新需求优先考虑能否复用现有概念。
4. **状态持久化**：任何 `reset` 后还需要的信息（工单、依赖、待回答的问题）都必须是持久化状态。
5. **可观测、可控制**：每个工单、Worker 和后台作业都能查看，用户随时可以中止或介入。

正常路径由 Engine 自动流转；意外情况交给 Router；只有必须由用户决定的事情才请示用户。
