# 记忆

## 1. 范围

记忆收录跨会话长期有用的合作经验：

| 记忆库 | 用途 | 边界 |
|---|---|---|
| **项目记忆库** | 保存当前项目的长期经验 | 可以按主题组织文件 |
| **全局记忆库** | 保存跨项目适用的合作约定 | 只允许编辑已有的 `MEMORY.md`，不开放新建、删除或重命名 |

Git 只是记忆库内部的版本管理细节，由记忆存储封装。用户和模型面对的是文件、变更与提案，不需要了解或直接操作 Git。所有角色都能读取记忆。

| 应当记录 | 应当舍弃 |
|:-:|:-:|
| 用户的偏好与风格 | 交接小结 |
| 用户纠正 | 任务进度与状态 |
| 带理由的架构/实验决策 | 随时能从文件里重新查到的事实 |
| 经验教训 | 密钥与敏感凭据 |

## 2. 格式

- `MEMORY.md`：常驻索引，控制在 200 行以内，存放每个对话都需要知道的核心约定，以及指向主题文件的索引（如 `[[optics-sim]]`）和简要说明。
- 项目中的主题文件按内容组织经验条目，每条附来源和日期；全局约定保持集中，不扩展为另一套主题目录。

## 3. 读取

- **常驻**：全局和项目的 `MEMORY.md` 放在每个对话的开篇最前面，运行中途不变。
- **按需**：模型根据索引读取相关主题，不把全部历史塞进每次对话。
- 已生效的记忆会进入之后新建或重新开始的对话；待审批的提案不作为既定经验。
- 读取文件与历史不产生变更，不能因为查看记忆就顺带保存手动修改。

## 4. 写入

执行对话只读不写：发现的经验写进报告，由 Router 或 Dreaming 提炼。

用户可以直接从 Web UI 编辑记忆，也可以在磁盘上手动修改；这些修改直接生效，记录为用户变更，不需要再走审批。

Router 和 Dreaming 对两个记忆库的所有修改都只能提出提案，只有用户批准后才生效。编辑、新建、替换、删除、重命名与撤销都遵守同一条边界，不能借全局记忆或撤销绕过审批。

同一次运行中的普通编辑，按记忆库分别合成一个提案，在运行结束时提交用户审阅。这样用户看到的是一次完整整理，而不是被每个细小动作打断。尚未提交的编辑应能跨重启保留，但不能提前写入记忆。

撤销形成独立提案，也需要用户批准。撤销不是抹去历史，而是在获批后增加一次反向变更。

用户审阅时应能看到文件差异，再决定批准或拒绝，也可以附上拒绝理由。批准后的结果交给 Router 留档，不因此唤醒它；拒绝或过期的提案则连同理由或冲突文件交回 Router，唤醒它重新判断、调整或提案。Dreaming 的结果也交给 Router，不依赖原整理工单仍然开放。

**过期**意味着提案依据的文件内容在提出后发生了变化。批准时必须重新确认，不能把后来出现的用户修改覆盖掉；发生冲突时整份提案都不生效。

**变更**是记忆库中已经生效的版本单位。用户修改与获批的模型提案分开记录，保留各自来源和相关工单；用户批准不把模型提案的来源改成用户。待审批、被拒绝或过期的提案不混入已生效的变更历史。

## 5. Dreaming

Dreaming 是后台记忆维护能力，它顺着地址回顾近期记录和现有记忆，尤其是反映真实执行结果的工具输出与报告里的经验教训，提出四类整理建议：

- **合并重叠笔记**：把同类条目整合进清晰的主题文件；
- **剔除临时细节并纠错**：删掉只对单次调试有效的信息，订正被后续执行推翻的旧笔记并注明来源；
- **清理陈旧记忆**：移除已经失效或长期没有价值的条目；
- **补漏与整理索引**：补录漏记的经验，维护 `MEMORY.md`，把过长的项目细节下沉到主题文件。

**触发**：不按固定时钟运行。自上次整理以来积累了足够的新材料，且项目空闲（Router、Worker 与后台作业都不在运行）一段时间后，Engine 开一张整理工单；两次整理之间保持最小间隔，同一时间至多一张。阈值属于可调整的运行策略。

只要 Dreaming 还有待审批的提案，就不再启动下一轮整理，避免围绕尚未生效的建议反复维护。整理工单结束只表示建议已经提交，不表示记忆已经改变。
