# 架构与 API 约定

架构的目标是让领域规则、运行机制和交互界面可以分别演进，而不是为每种入口复制一套行为。

## 1. 进程模型

Engine 持有持续运行的工作与持久状态，不依附于浏览器页面或某次 CLI 调用。关闭面板不应中断项目。

CLI 负责启动、停止和发现 Engine；Web UI 是用户观察、对话与控制工作的交互面。CLI 不再提供另一套项目操作界面。

### 运行生命周期

同一数据目录只允许一个 Engine。运行发现与本地 API 授权属于同一个实例的生命周期；重启后应重新授权，不能仅凭端口或进程号把另一个实例认作原实例。CLI 可以脱离终端启动，也可以以前台方式运行；停止成功意味着实例已退出，而不仅是收到停止请求。

实例锁负责排他，运行发现负责确认身份，两者不能互相替代。启动失败或正常退出时都要释放占用，避免一次失败阻塞后续使用。

## 2. 分层与依赖

按基础能力到外部入口，系统分为：

**domain → config/protocol → engine → server → daemon/cli**

箭头表示构建顺序，不是导入方向。实际依赖从外向内，只能使用约定开放的基础层，不能让内部规则反向认识外部入口。

- **domain**：领域概念与规则，不依赖运行环境或交互方式。
- **config / protocol**：分别表达配置约束与交互约定，不承担 Engine 的运行行为。
- **engine**：组合领域能力，管理项目、对话与工作流，不关心请求来自哪个界面。
- **server**：把协议请求交给 Engine，并把结果转为对外响应，不另写一套业务规则。
- **daemon / cli**：负责进程装配与生命周期；CLI 通过启动入口和协议与 Engine 协作。

Web 只接触 domain、protocol 和 config，不直接复用 Engine 内部逻辑。界面需要的新能力应成为明确的协议，而不是跨越边界取用内部状态。

这些依赖边界由测试强制检查，而不只依靠约定。代价是增加少量转换与装配，换来规则可独立验证、内部改动不向所有入口扩散。

## 3. Engine 的组织

编排核心决定工单如何流转、结果如何投递、运行如何收尾；这些规则不应绑定于模型通过哪种工具发起操作。

Durable 工具适配负责接入工具调用、解释输入与转换结果，再委托编排核心。核心不依赖工具适配或角色装配，使工作流能脱离模型调用单独验证。

项目是一组聚焦服务的组合，而不是包办所有行为的入口。对话、提问、后台作业、记忆、视图与设置各自承担职责。

服务只依赖完成工作所需的能力，不通过整个项目间接取得任意状态。组合处负责把它们接起来，避免项目边界演变成隐式的全局依赖。

Router 与 Worker 的对话统一寻址，读取、发送、打断等操作使用同一套抽象。角色差异仍由服务集中判断；统一入口不意味着 Router 与 Worker 具有相同权限。

## 4. API 约定

API 面向资源及其关系，而不是把内部操作逐个翻译成 RPC。客户端表达对项目、对话和记忆的意图，不需要了解 Engine 如何完成工作。

服务端与客户端共享一份协议定义，避免请求约定在两端各自维护。协议描述对外承诺，不暴露内部对象的组织方式。

路径参数与请求内容在边界校验并解释，再交给内部服务。无效输入应作为可预期的问题返回，而不是让错误的标识继续流入工作流。

边界校验不能替代领域判断：形式正确的请求，仍可能因角色限制或当前工作状态而被拒绝。

只表达动作、没有结果载荷的命令成功后不返回正文；有资源结果的变更返回更新后的资源，让界面据此更新，而不是自行猜测结果。

错误以问题文档表达，使用稳定的问题码承载语义。HTTP 状态提供通用分类，文字说明帮助用户理解，两者都不能替代问题码。

客户端可以本地化问题说明，但不应通过匹配英文句子判断错误种类。可预期的业务拒绝与意外失败都应经过统一的错误边界。

## 5. 状态同步

REST 保留一次性读取与提交操作的用途；持续观察交给流订阅，不让每个页面各自轮询和拼凑状态。

流同时承载 Engine 级与项目级主题：前者反映实例与项目概况，后者反映项目内的看板和对话。

订阅先给出当前视图，再推送后续变化。界面重连后应能重新建立一致的观察，而不是把连接期间收到的消息当成唯一事实来源。

项目摘要在短时间内的连续变更可以合并推送。订阅关注可见状态，不要求每次内部写入都产生一次独立通知。

流通过带版本的子协议协商语义。协议发生不兼容变化时应明确区分版本，不依赖新旧客户端碰巧能理解同一条消息。
