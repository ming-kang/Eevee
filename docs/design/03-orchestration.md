# 工单与调度

总体设计：正常路径自动流转，意外情况交给 Router，必须由用户决定时才提问。

## 1. 拓扑

**自动协调经过 Router，数据通过文件和地址传递；用户可以直接介入任何 Worker。**

- **Router 像塔台与运控**：掌握全局目标，安排工单、优先级与时序，处理报告、验收和异常，不替 Worker 处理执行细节。
- **用户以 Router 为主要入口**：也可以观察 Worker、直接发送引导或打断。Worker 不独立向用户推送通知，自动结果仍通过 Report 交给 Router。
- **Router 不执行耗时工作**：`router` 角色没有工作区写入与 `bash` 工具，避免它亲自干活而阻塞全局协调。
- **确定事项由 Engine 投递**：依赖工单的结果、问题的回答、后台作业的结果，由 Engine 按规则直接投给对应 Worker，不绕经 Router 转述。

## 2. 工具

### Router

| 工具 | 动作 / 参数 | 作用 |
|:-:|---|---|
| `ticket` | `create`（目标、输入、验收标准；可选输出位置、模型覆盖及理由、`deliverTo`） | 建单并启动 Worker；缺省模型使用角色或项目配置 |
| | `message`（引导或排队，见下） | 给执行对话追加指令 |
| | `interrupt` | 打断执行对话当前这一轮，工单仍为 `open` |
| | `review`（`accept` + 证据，或 `rework` + 缺什么） | 处理 `ready` 报告：结单为 `done`，或打回接着做 |
| | `close`（原因） | 取消工单，结单为 `cancelled` |
| | `model`（provider、模型、理由） | 给执行对话换模型，从下一次请求起生效 |
| `ask_user` | 问题列表，可选 `ticketId` | 写入 `Question` 后立即返回，不等待 |
| `read` | 地址、分页、`query` | 见 [资源地址](../addresses.md) |
| `memory` | `edit` / `create` / `log` / `diff` / `revert` | 见 [04 记忆](04-memory.md) |
| `handoff` | 交接小结 | 交接：写下小结并重置自己的上下文，见 [重置](../how-eevee-works.md#重置) |

对方正在运行时，追加的消息有两种进入方式：**引导**（Durable 的 `steer`）在当前这批工具调用结束后立刻被看到；**排队**（`followUp`）等这一轮结束后再开始新的一轮。对方空闲时两者一样，都直接开始新的一轮。

### Worker

`worker` 角色的基础工具是 `read` / `write` / `edit` / `bash` / `report`，`dreamer` 使用 `read`、只能整理项目记忆的 `memory` 和 `report`。

MCP 服务器、用户扩展等在 `settings.json` 里按角色启用，见 [02 角色与能力](02-roles.md) 与 [配置角色能力](../capabilities.md)。

## 3. 报告

报告是 Worker 的**自动协同出口**，状态分两类：

| 类别 | 状态 | 含义 | `report` 工具的行为 | 对 Router |
|:-:|:-:|:-:|:-:|:-:|
| 中途报告 | `progress` | 有阶段性进展 | 本轮继续 | 不主动唤醒 |
| 收尾报告 | `waiting` | 缺少材料，在`need`中写明 | 结束本轮（`terminate: true`） | 唤醒 |
| | `ready` | 做完了，等验收 | 同上 | 同上 |
| | `blocked` / `failed` | 无法继续 / 失败 | 同上 | 同上 |
| | `dropped` | 发现不需要做 | 同上 | 同上 |

- **原子投递**：`report` 在同一个 commit 里写入报告文档，并用 `submit(tx, draft)` 向 Router 提交，`requestId` 取 `report://t12#3`。不需要单独的 reporter 任务，重启也不会重复投递。
- **摘要限长**：投给 Router 的只有状态、600 字以内的摘要、产物列表和报告地址；`detail` 留在文档里按需 `read`。
- **问题与经验结构化**：需要用户决定的问题写进 `questions`，值得记住的经验写进 `lessons`，不靠 Router 从摘要里去猜。
- **兜底**：执行对话一轮结束时，Engine 检查本轮是否交过收尾报告。没交、并且也没有运行中的后台作业时，用最后一段回答补一份 `waiting`。运行失败（重试用尽、超出 `maxTurns`）由 Engine 记一份 `failed`，摘要写明失败原因，`need` 提示用 `ticket message` 让它继续或取消工单；中止、重置等有意的结束不算失败。

## 4. 工单阶段

工单状态为 `open` / `done` / `cancelled`。`open` 工单在界面上的阶段按下表从上往下取第一个匹配：

| 阶段 | 条件 | 需要谁 |
|:-:|:-:|:-:|
| 待回答 | 有归属于它、尚未回答的 `Question` | 用户 |
| 待验收 | 最新收尾报告是 `ready`，且未处理 | Router |
| 受阻 | 最新收尾报告是 `blocked` / `failed` / `dropped`，且未处理 | Router |
| 排队 | 等并发槽位 | — |
| 工作中 | 执行对话正在运行 | — |
| 后台作业 | 本轮已结束，但有后台作业在跑 | — |
| 等待 | 最新收尾报告是 `waiting` | Router 或依赖工单 |
| 闲置 | 其他情况 | — |

## 5. 投递表

所有事件都经过同一个 `route(event)`，得到投给谁、用什么方式；工具和 Engine 都按它的结果提交。投递方式只有两种：

- **唤醒**（Durable 的 `input`）：对方空闲就开始新的一轮，忙时按表中注明的引导或排队进入；
- **不主动唤醒**（Durable 的 `write`）：不自行启动新一轮。纯 `kind` / `data` 条目立即追加、模型看不到；带 `model` 的条目等下一个对话边界才对模型可见，随之后的运行被看到。

| 事件 | 目标 | 方式 |
|:-:|:-:|:-:|
| 工单创建 | 该执行对话 | 建单时把开篇写入对话（不唤醒）；开始运行只由空闲槽位决定，见第 8 节 |
| 用户在主对话发言 | Router | 唤醒（忙时引导） |
| 收尾报告 | Router | 唤醒（忙时排队） |
| 中途报告、工单结单等状态变化 | Router | 不主动唤醒 |
| 工单被 `accept`，且 `deliverTo` 非空 | `deliverTo` 里的每个执行对话 | 唤醒：报告地址 + 摘要 + 产物；Router 不主动唤醒 |
| 工单被取消，且有工单在等它 | Router | 唤醒 |
| 用户回答了问题 | 问题归属 Router：Router；归属工单：该执行对话 | 唤醒；归属工单时直接投递，不排队等槽位；Router 另外不主动唤醒地记录 |
| 后台作业结束 | 所属执行对话 | 唤醒 |
| Engine 重启打断了后台作业 | 所属执行对话 | 唤醒：哪些作业被打断，提醒先检查目录和 git 状态再决定是否重跑 |
| `dreamer` 工单的报告 | Router | 不主动唤醒；`ready` 自动验收 |
| 用户在面板直接给 Worker 发消息 | 该 Worker | 唤醒（忙时引导）；Router 不主动唤醒地记录这次介入 |

## 6. 主动推进

每份收尾报告带一个“已处理”标记（`handled`），使未处理结果成为 Router 的持久待办，不依赖对话里是否还记得：

- **何时算已处理**：Router 对该工单采取相关 `ticket` 动作、为它 `ask_user`，或新建 `deliverTo` 包含它的工单，就把它最新的收尾报告标为已处理。依赖结果由 Engine 直接投递时，对应的 `waiting` 报告也标为已处理。
- **持续可见**：未处理报告保留在 Router 待办中。Engine 可以提醒 Router；提醒时机和次数是当前实现策略，不进入核心领域模型。
- **交给用户**：Router 仍无法推进或需要用户决定时，报告进入面板“等待介入”区。正常情况下不因为执行进展而打扰用户。

## 7. 对齐与验收

- **对齐**：需求清楚就直接建单；不清楚时，能从工作目录和记忆里查到的，Router 自己 `read` 或建单去查；只有真要用户拍板的分歧，才用 `ask_user` 整理成一轮编号问题，每题附推荐答案。
- **执行对话的疑问**：写进报告的 `questions`。Router 能自己回答就 `ticket message`，否则带上 `ticketId` 转成 `ask_user`，用户的回答会直接投给那个执行对话。
- **回答只认第一个**：写入答案的 commit 同时确认这个问题还没有被回答、也没有随工单被撤下，并且只投递一次；并发提交的第二个答案会收到 `answered`，不会覆盖第一个。
- **验收**：`review accept` 必须附证据（测试输出、改动的文件、检查结果），记入工单的 `closeNote`。验收在同一个 commit 里确认那份 `ready` 报告仍是最新且未处理，被后来的报告取代时返回 `report_changed`，Router 看最新一报再决定。需要另一张工单确认时（比如图要论文工单认可），Router 把产物地址 `message` 过去，拿到确认后再 `accept`。验收是 Router 的内部协同动作，无需用户审批执行步骤。

## 8. 并发与后台作业

这些是运行策略，不引入新的领域概念，默认值可以调整：

- **并发槽位**：当前方案以 `maxActiveWorkers`（默认 3）限制同时运行的 Worker。建单时目标、验收标准和开篇已经写进执行对话，排队排的只是“开始运行”；槽位空出后用一次 `continue` 开始，不追加消息。Router 不占槽位；用户直接介入已有 Worker、回答问题都不应被新工单挡住。槽位以对话真实空闲为准，`afterRun` 任务尚未完成时仍算忙碌。
- **后台作业**：长命令可以转入后台，立即返回 `job://j7`，输出写入 `jobs/<jobId>.log`。当前方案是前台命令超过 5 秒自动转后台，之后也可以支持 Worker 显式选择后台执行；阈值和选择方式都不是领域规则。
- **结果回流**：Worker 可以在作业运行时结束本轮、释放槽位；作业结束后结果唤醒它。本轮结束时有作业在跑，不触发兜底的 `waiting` 报告。
- **结单清理**：工单结单时终止它仍在运行的后台作业，Worker 主对话随工单结束。

## 9. 结单

`open` 是工单唯一的非终态，离开它只有一个动作：一次终态转换，`review accept`、`ticket close` 和 `dreamer` 自动验收都走它。

- **同一个 commit 里做完**：重新读工单（必须仍是 `open`）、验收时核对最新收尾报告仍是 Router 看到的那一份（否则 `report_changed`）、写 `status` 与 `closeNote`、把该工单未回答的问题撤下（`Question.withdrawnAt`，并从 `openQuestions` 移除）、清掉还在等它的投递。
- **停止执行是持久意图**：结单后 Engine 停止关联的后台作业并终止执行对话，再把 `stoppedAt` 写进工单。这一步可以补做：进程在这之前退出时，重启后的扫描会接着做完。`stoppedAt` 也是“已经停过”的记录，重启不会重复处理。
- **结单后不再有输入**：终止对话本身不阻止新的输入，所以入口都会校验状态——面板消息、重试、`ticket message` 看工单是否仍为 `open`，`report` 和 `ask_user` 在写入的同一个 commit 里再确认一次，排队中的投递在结单时被清掉。
