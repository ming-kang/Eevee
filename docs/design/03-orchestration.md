# 工单与调度

总体设计：正常路径自动流转，意外情况交给 Router，必须由用户决定时才提问。

## 1. 拓扑

**自动协调经过 Router，数据通过文件和地址传递；用户可以直接介入任何 Worker。**

- Router 掌握全局目标，安排工单、优先级与时序，处理报告、验收和异常，不替 Worker 处理执行细节。
- 用户以 Router 为主要入口，也可以观察 Worker、直接发送引导或打断。
- Router 不执行耗时工作，它没有工作区写入与 `bash` 工具，避免它亲自干活而阻塞全局协调。
- 确定事项由 Engine 投递，依赖工单的结果、问题的回答、后台作业的结果，由 Engine 按规则直接投给对应 Worker。

## 2. 工具

### Router

| 工具 | 动作 / 参数 | 作用 |
|:-:|:-:|---|
| `ticket` | `create` | 建立工单并启动 Worker |
| | `message` | 向执行对话追加指令 |
| | `interrupt` | 打断执行对话当前轮次 |
| | `review` | 处理 `ready` 报告：结束工单或打回重做 |
| | `close` | 取消工单 |
| | `model` | 为执行对话设置模型，从下一次请求起生效 |
| `ask_user` | 问题列表（可附带 `ticketId`） | 以非阻塞方式向用户提问 |
| `read` | 地址、分页、`query` | 引用持久对象的统一地址，见 [01 概念](01-concepts.md) |
| `memory` | `edit` / `create` / `history` / `show` / `undo` | 见 [04 记忆](04-memory.md) |
| `handoff` | 交接小结 | 写下当前小结并重置自己的上下文 |

追加的消息有两种进入方式：**引导**（`steer`）在当前这批工具调用结束后即刻进入；**排队**（`followUp`）等这一轮结束后再进入。

### Worker

`worker` 角色的基础工具是 `read` / `write` / `edit` / `bash` / `report`。

`dreamer` 使用 `read`，整理项目记忆的 `memory` 和 `report`。

MCP 服务器、用户扩展等在 `settings.json` 里按角色启用，见 [02 角色与能力](02-roles.md)。

## 3. 报告

报告是 Worker 的协同出口，状态分两类：

| 类别 | 状态 | 含义 | `report` 工具的行为 | 对 Router |
|:-:|:-:|:-:|:-:|:-:|
| 中途报告 | `progress` | 有阶段性进展 | 本轮继续 | 不主动唤醒 |
| 收尾报告 | `waiting` | 缺少材料（在`need`中写明） | 结束本轮（`terminate: true`） | 唤醒 |
| | `ready` | 等待验收 | 同上 | 同上 |
| | `blocked` / `failed` | 无法继续 / 失败 | 同上 | 同上 |
| | `dropped` | 发现不需要做 | 同上 | 同上 |

- **问题与经验结构化**：需要用户决定的问题写进 `questions`，值得记住的经验写进 `lessons`。
- **兜底**：执行对话一轮结束时，Engine 检查本轮是否交过收尾报告。如果没交且也没有运行中的后台作业时，用最后一段回答作为 `waiting` 报告补交。运行失败由 Engine 补充一份 `failed`，摘要写明失败原因，`need` 提示用 `ticket message` 让它继续或取消工单；中止、重置等有意结束不算运行失败。

## 4. 工单阶段

工单状态为 `open` / `done` / `cancelled`，`open` 工单在界面上的阶段按下表从上往下取第一个匹配：

| 阶段 | 条件 | 需要谁 |
|:-:|:-:|:-:|
| 待回答 | 有归属于它、尚未回答的 `Question` | 用户 |
| 待验收 | 最新收尾报告是 `ready`，且未处理 | Router |
| 受阻 | 最新收尾报告是 `blocked` / `failed` / `dropped`，且未处理 | Router |
| 排队 | 等待并发槽位 | — |
| 工作中 | 执行对话正在运行 | — |
| 后台作业 | 本轮结束，但有后台作业进行 | — |
| 等待 | 最新报告是 `waiting` | Router 或依赖工单 |
| 闲置 | 其他情况 | — |

## 5. 投递表

所有事件都经过同一个 `route(event)`，工具和 Engine 都按它的结果提交。投递方式：

- **唤醒**：对方空闲就开始新的一轮，忙时引导或排队；
- **不主动唤醒**：`kind` / `data` 条目立即追加；带 `model` 的条目等下一个对话边界才对模型可见。

| 事件 | 目标 | 方式 |
|:-:|:-:|:-:|
| 工单创建 | 该执行对话 | 不主动唤醒 |
| 用户在主对话发言 | Router | 唤醒（忙时引导） |
| 收尾报告 | Router | 唤醒（忙时排队） |
| 中途报告、工单等状态变化 | Router | 不主动唤醒 |
| 工单被 `accept` 且 `deliverTo` 非空 | `deliverTo` 里的执行对话 | 唤醒 |
| 工单被取消且有工单在等它 | Router | 唤醒 |
| 用户回答问题 | 问题所属会话 | 唤醒 |
| 后台作业结束 | 所属执行对话 | 唤醒 |
| Engine 重启 | 所属执行对话 | 唤醒 |
| `dreamer` 工单报告 | Router | 不主动唤醒 |
| 用户在面板直接给 Worker 发消息 | 该 Worker | 唤醒（忙时引导） |

## 6. 主动推进

每份收尾报告带一个“已处理”标记（`handled`），使未处理结果成为 Router 的持久待办：

- **持续可见**：未处理报告保留在 Router 待办中。Engine 可以提醒 Router。
- **交给用户**：Router 仍无法推进或需要用户决定时，报告进入面板“等待介入”区。

## 7. 对齐与验收

- **需求对齐**：讨论清楚后建立工单；需求模糊时，Router 从工作目录、记忆等收集信息，可以建立工单辅助探索；将需要用户介入的分歧用 `ask_user`，每附带推荐答案。
- **执行对话的疑问**：写进报告的 `questions`，Router 能自己回答就 `ticket message`，否则带上 `ticketId` 转成 `ask_user`，用户的回答直接投递给相应执行对话。
- **验收**：`review accept` 必须附带证据，记入工单的 `closeNote`。

## 8. 并发与后台作业

这些是运行策略，默认值可以调整：

- **并发槽位**：当前方案以 `maxActiveWorkers`（默认 3）限制同时运行的 Worker。
- **后台作业**：长命令可以转入后台，立即返回 `job://<jobId>`，输出写入 `jobs/<jobId>.log`。
- **结果回流**：Worker 可以在作业运行时结束本轮、释放槽位；作业结束后结果唤醒它。
- **结单清理**：工单结单时终止它仍在运行的后台作业，Worker 会话随工单结束。

## 9. 结单

`open` 是工单唯一的非终态。
